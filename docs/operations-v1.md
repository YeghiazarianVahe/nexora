# Candidate operations, installation and recovery

This describes repository candidate behavior. No production installation or recovery was performed by remediation. The working pilot remains unchanged. Domain-joined disposable Windows VM install/upgrade/uninstall and reboot/endpoint-protection validation are still required.

## Prerequisites and deployment

Windows domain membership and an approved operator/service identity, .NET 10 compatible runtime (API) or approved self-contained publication, enterprise browser integrated-auth policies, HTTP.sys URL reservation, Domain-profile firewall scope, PostgreSQL 16+ tools/runtime, initial SuperAdmin SID and protected private data directory are required. Do not open additional profiles or remote database listeners. CredentialOps remains false; Diagnostics remains intentionally true. Preflight must verify available disk space, writable protected log/data folders, expected bindings, trust key availability, helper compatibility and pending migrations before change approval.

Build a new empty staging directory with `scripts/New-NexoraCandidate.ps1 -OutputDirectory <absolute-staging-path>`. It builds API/web/helper together, emits source and artifact checksums, toolchain and dependency inventories, and never starts or deploys them. The helper is unsigned and unstamped; do not distribute it directly as a trusted production helper. This working-tree recipe is not an immutable/signed release claim. Use `scripts/nexora.ps1 -InstallPath <candidate-api-path>` on an approved disposable machine only; preserve that machine's explicitly reviewed settings/data path. A staging directory is not an authorized replacement for the pilot.

`nexora.ps1 -Action Install` includes installation/upgrade of `Nexora-LocalDiskTelemetry`; `Status` reports task/result/source freshness; `Uninstall` removes only its recognized fixed SYSTEM task and known collector files. Standalone `install-local-disk-telemetry.ps1 -Action Install|Status|Uninstall` is supported. Install/removal requires administrator rights. `-WhatIf` provides a no-change standalone plan. The fixed task reads native disk evidence every minute. Dedicated child ACLs permit writes only to Administrators/SYSTEM and ordinary users read access. Parent ownership/ACL safety and linked-file checks are mandatory; unrelated parent files, tasks and directories are retained. Upgrades stop only a recognized running collector before atomic script replacement. A hidden SYSTEM task may require elevation to inspect its scheduler status. No installer was executed on the pilot during remediation.

Helper logon deployment starts existing signed-in sessions through Task Scheduler RunEx where authorized; otherwise a later sign-in starts the user helper. It never launches an interactive helper as SYSTEM. Administrative maintenance jobs are different: selected fixed scripts execute as SYSTEM through an operator-authorized one-off task. Admin is required for profile deletion; Operator can inspect profiles and perform permitted service/process jobs. Always consult server-side catalog/risk checks, not just UI visibility.

## Backups

File deployment backups exclude live database data and are insufficient for recovery. Use `Backup-NexoraDatabase.ps1` with explicit PostgreSQL tool directory, source host/port/database/user, and a **new dedicated empty backup directory**. Passwords come from a protected PGPASSFILE/pgpass, never command arguments, reports or source control. The tool protects the directory, creates a custom archive, verifies pg_restore can list it, and writes a SHA-256 manifest. A listed archive is not yet a verified recovery. Only synthetic isolated data was used in the remediation restore test.

Configuration recovery must include the authorized runtime configuration and references to separately protected secrets. `Backup-NexoraConfiguration.ps1` exports a whitelisted non-secret configuration view; it does not claim to back up credentials or private keys. Keep actual secret backups in the organization's approved secret/backup service, outside QA artifacts. Preserve connection/identity references, PostgreSQL cluster settings and migration inventory through that approved process.

## Disposable restore

`Restore-NexoraDisposableDatabase.ps1` deliberately supports loopback only, forbids port 5434, requires an existing empty database named `nexora_restore_<suffix>`, a matching archive checksum, and a marker file containing `nexora-disposable-restore-v1:<32-lowercase-hex-GUID>`. It uses a single transaction and exit-on-error; it does not drop databases, overwrite populated schemas or restore production. The isolated test creates a temporary PostgreSQL cluster on an ephemeral port, backs up synthetic rows, restores an empty target, and checks row contents. Full enterprise restoration, audit-trigger/migration/data-volume recovery, RPO/RTO and host-loss recovery need separate acceptance even when that synthetic test passes.

DPAPI-protected server trust material is bound to the relevant Windows account/machine context. Copying an encrypted blob to another host/account does not prove recovery. Restore on an equivalent approved identity or plan explicit helper re-pairing/reprovisioning. Never export the pilot's private key into QA. Public trust fingerprints may be compared without exposing private material.

## Upgrade, rollback and availability

Before deployment, preserve database/configuration/trust backups, verify archive integrity, rehearse restore, inventory migrations, and drain or explicitly account for active jobs. Do not assume a previous binary can use a new schema. Row-version validation uses PostgreSQL's existing xmin system column: no application schema column or migration is added for the disk-refresh guard. Additive API metadata remains compatible with older clients/helpers. Model 7 causes scores from previous versions to be identified as earlier evidence pending a normal future collection; remediation does not trigger production rescans.

Current scripts launch API/private PostgreSQL as processes. A production reboot-startup/watchdog/service policy must be explicitly provisioned and approved; none is silently installed here. Existing job recovery/retention and reconnect tests cover isolated cases, not every host-loss scenario. Keep DB availability checks, bounded collector timeouts and stale-evidence status observable. Do not raise the four-worker live collector limit without representative measurements. Meter `Nexora.LivePerformance` exports requests, failures and duration; `Snapshot` exposes active/queued counts. Timeout/cancellation retains a slot until an underlying call actually finishes, bounding abandoned work.

For outages, check health/DB connectivity, protected structured logs with correlation references, helper identity/version, local task result/time, available disk space and connectivity. A local source older than two minutes is last-known; after ten minutes the cache explicitly says expired. It remains useful historical health, never a current temperature. Preserve data on disk-full/permission failures; do not purge audit records or disable safety checks to recover capacity. Crash/reboot, full-disk, scheduled-task failure and long soak tests remain disposable-VM gates.
